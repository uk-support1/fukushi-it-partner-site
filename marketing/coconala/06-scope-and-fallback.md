# 06 確認範囲と、PHPの版が確認できない場合の対応

2026年10月23日の方針決定（`03-product-plan.md` §10）を受けて作成。出品文（`04-listing-copy.md`）と画像（`05-image-plan.md`）は、この文書に合わせています。

## 1. 呼び方：商品名・出品文では「診断」と呼ばない

福祉ITパートナーは、サイトで「脆弱性診断や、攻撃を受けたかどうかの調査は行っていません」と公表しています（`php-homepage-comparison.html`、`homepage-cost-reduction.html`）。ココナラの有料の基本プランは、その方針の範囲内の **「PHPの版の確認と、今回の脆弱性への該当の確認（書面での報告）」** です。

- 商品名・出品文・画像では、**「確認」「ご報告」**と書きます。「診断」「点検」は使いません。
- 社内で「有料診断」と呼ぶときも、中身は「確認と報告」です。攻撃を試すテストや、侵害の調査は含みません。

## 2. 無料の診断（サイト）との役割分担【採用】

| | 福祉ITパートナーの「HP維持費削減診断」（0円・サイト） | ココナラ 基本プラン（有料・2,000円） |
| --- | --- | --- |
| 目的 | 費用・契約の見直し。乗り換えが向くか、今のままがよいかを一緒に考える | **PHPの版と今回の脆弱性への該当を調べ、書面で報告する** |
| 中身 | 契約内容とホームページの仕組みを一緒に整理する（相談） | PHPを使っているかの確認、PHPの版の確認、今回の修正版との比較、4段階の判定、必要な対策 |
| 成果物 | 相談・お見積りのご案内 | **報告書（PDF 1〜2枚）とチャット** |
| 入口 | サイトの問い合わせ | ココナラ |
| 行わないこと | 脆弱性診断、攻撃を受けたかの調査 | 同じ |

**運用のルール**
1. サイトの0円診断では、PHPの版の確認結果を、書面の報告として出さない。版の書面報告を希望された方には、ココナラの基本プランを案内する（サイトからココナラへの案内は問題ない）。
2. ココナラのトークルームや説明文から、サイトの0円診断や問い合わせフォームへ誘導しない（ココナラの外部誘導の禁止）。乗り換えの相談は、ココナラの「見積り相談」で受ける。
3. サイト側の文言は、今回は変更しない。

## 3. 確認範囲

### 3-1. 確認すること

| 項目 | 何を見るか | 根拠にする情報 |
| --- | --- | --- |
| PHPを使っているサイトか | サイトの種類（WordPressなど）、サーバー会社 | お客様からのご説明、画面、ご依頼のサイトを通常どおり表示したときに見える範囲 |
| **PHPの版** | 実際に動いているPHPの版 | **お客様に送っていただく画面に表示された値**（§4） |
| 今回の修正版との比較 | 8.5.12／8.4.27／8.3.36／8.2.35 との比較 | 公式の修正版の番号（`01-fact-check-php-vulnerability.md`） |
| サポート状況 | 8.1以前（更新が出ない）、8.2系（2026年12月31日で終了） | PHP公式 |
| PHPを誰が管理しているか | お客様が選べるか、サーバー会社が管理しているか | 画面、お客様のご説明 |
| 参考情報（任意） | 画面に写っている範囲の、WordPress本体の版・更新の表示など | **気づいた点のお伝えのみ。網羅的な確認ではありません** |

### 3-2. 確認しないこと

| 項目 | 理由・案内先 |
| --- | --- |
| 脆弱性診断（攻撃を試すテスト） | 行わない方針（サイトと同じ）。必要な場合は専門の業者へ |
| 攻撃を受けたかどうかの調査、ログの解析、マルウェア（ウイルス）の除去 | 行わない方針。ご心配な場合は、サーバー会社や専門の業者へ。確認の観点の一般的な例（JPCERT/CC）は、ご報告でお伝えできる |
| サーバーの設定（メモリ上限など）の確認・変更 | サーバー管理者向けの内容で、設定だけでは完全な対策にならない（公式）。更新を優先する |
| WordPress本体・テーマ・プラグイン個別の脆弱性 | 今回の件とは別の確認。基本プランに含まない |
| サーバー会社の対応状況の代理確認 | お客様からサーバー会社へ確認していただく。そのための文例をお渡しする |
| サイト全体のセキュリティ（パスワード、SSLなど） | 範囲外 |
| 「安全です」というお約束 | しない |

### 3-3. 判定の根拠と限界（ご報告に必ず書く）

- 判定は、**お客様からいただいた情報（画面）が表示していた内容と、ご報告の日付の時点**にもとづきます。
- **外から見える表示（応答ヘッダなど）は「参考」で、確定の根拠にしません。** 設定で隠したり変えたりできるためです。
- **PHPの番号が同じでも、サーバー会社やOSの提供元が、番号を変えずに修正を済ませている場合があります**（PHP公式、JPCERT/CC）。逆に、番号が古く見えても対応済みのことがあります。そのため、番号だけで判断できないときは「？要確認」とし、確認先をお伝えします。
- サーバー会社が、更新の前に、脆弱性を緩和するWAFルールなどを入れている場合もあります（WordPress公式）。これは更新の代わりにはなりません（PHP公式：完全な対策は更新のみ）が、確認先への質問に含めます。

## 4. PHPの版の調べ方（優先順位）

| 順 | 方法 | 使いどころ |
| --- | --- | --- |
| 1 | WordPressの管理画面：**ツール → サイトヘルス → 情報 → サーバー**（WordPress公式の告知で案内されている手順。表示名はWordPressの版で少し違うことがある） | **Webで実際に動いているPHPの版が出るため、確定の根拠に使える。** 管理者の権限が必要 |
| 2 | サーバーの管理画面の、PHPの版を設定する画面 | 1に入れないとき。**「設定値」の表示で、実際に動いている版と、反映のタイミングが違うことがある**ため、1で確認できるときは1を優先する。メニュー名はサーバー会社ごとに違う（各社の名称は、公式マニュアルで確認が取れていないため、ご案内では「PHP」「PHPバージョン」などの項目を探す、という書き方にする） |
| 3 | サーバー会社・制作会社からの回答 | 1・2が難しいとき。問い合わせの文例をお渡しする（§6） |
| 4 | 外から見える表示（応答ヘッダなど） | **参考のみ。** 見えたときは「参考」と明記する。確定には使わない |

> コマンドライン用のPHPの版は、Webで動くPHPと別のことがあります。判定には、**Webで動いている版**を使います。

## 5. PHPの版が確認できないときの対応【決定】

どのケースも、**基本プランの料金のまま、追加費用はありません。** 版が確認できなかった場合も、「？要確認」の報告書（確認先と問い合わせの文例つき）が、基本プランの成果物です。

| # | ケース | 対応 | ご報告の判定 |
| --- | --- | --- | --- |
| A | 画面は送られたが、番号が写っていない・読めない | 撮り直しの方法を、画像つきでご案内する（お客様への再依頼は2回を目安） | 確認できれば通常の判定。できなければ「？」 |
| B | WordPressの管理画面に入れない（IDが分からない、制作会社が管理している） | サーバーの管理画面から確認する方法に切り替える（§4の2） | 同上 |
| C | サーバーの管理画面にも入れない（制作会社・サーバー会社が管理） | 問い合わせ先と文例をお渡しする（§6） | **？ 要確認** |
| D | サーバー会社がPHPを管理していて、お客様が番号を見られない・選べない | サーバー会社への問い合わせの文例をお渡しする（今回の修正の適用有無と日付、動作中の版） | **？ 要確認** |
| E | 番号は修正版より前だが、OSの提供元などが独自に修正している可能性がある（OS付属のPHP、専用サーバー・VPSなど） | 番号は事実としてお伝えしたうえで、**△ではなく「？」とし**、提供元への確認をおすすめする | **？ 要確認** |
| F | PHPを使っていない（HTMLだけのサイトなど） | 今回の脆弱性の対象ではない旨を報告する | **対象外** |
| G | 複数のサイト、またはドメインごとに別のPHPの版 | サイトごとに画面が必要。2つ目以降は有料オプション「追加サイトの確認」 | サイトごと |
| H | ご依頼後、情報が届かない・返信が止まった | 3日後・7日後に、トークルームでお声がけする。**7日を目安に、現時点の情報で「？要確認」の報告書を納品する** | **？ 要確認** |
| I | サイトが表示されない、エラーが出ている | 本サービスの範囲外（故障・障害）。サーバー会社への相談をご案内する | — |
| J | WordPress以外のPHPのしくみ（予約・会員・ネットショップなど） | 版の確認は、画面があれば基本プランで可能。更新は受けられないか、別見積りになる | 通常の判定 |

> **Hの「7日」と、キャンセル・返金の扱いは運用ルール案です。** ココナラのキャンセル・返金の規定は、原文で確認できていません。「確認できなかったので不要になった」というご希望は、トークルームでご相談のうえ、ココナラの規定に従って対応します。出品文には、返金やキャンセルの約束は書きません。

## 6. ご報告書の書き方（文例）

### 「？ 要確認」の結論の文例

> 【結論】？ 要確認
> いただいた情報では、PHPの版を確認できませんでした（理由：サーバー会社がPHPを管理していて、お客様の画面には番号が表示されないため）。そのため、今回の脆弱性に該当するかは、判断できません。
> 次の順に、確認をお願いします。
> 1. 下の文例を使って、サーバー会社へお問い合わせください。
> 2. 回答が届きましたら、トークルームにお知らせください。修正版であれば、「◎」としてご報告し直します（1回、追加料金なし）。
> なお、このご報告は、いただいた情報にもとづくもので、脆弱性診断や、攻撃を受けたかどうかの調査ではありません。

> **「回答が届いたら、ご報告し直します（1回、追加料金なし）」は運用ルール案**です。出品文には書かず、対応の目安として扱います。

### サーバー会社・制作会社への問い合わせ文例

> お世話になっております。契約中のホームページ（〈サイトのURL〉）について、次の点を教えてください。
> 1. 2026年10月21日に公開されたPHPの脆弱性（CVE-2026-109618、CVE-2026-109619）の修正は、適用済みでしょうか。適用済みの場合は、その日付も教えてください。（更新ではなく、緩和策のみの場合は、その旨も教えてください）
> 2. 現在、このサイトで動いているPHPのバージョンを教えてください。
> 3. PHPのバージョンは、お客様側の管理画面で選べますか。選べる場合は、変更の方法を教えてください。

CVE番号・日付は `01-fact-check-php-vulnerability.md` と一致しています。
